# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`@tamga/sdk` is the official JavaScript/TypeScript SDK for Tamga (license activation, offline verification, machine management), one of eight hand-written per-language SDKs rather than a binding over the shared `tamga-c` core. It is the only Tamga SDK that must run correctly across four distinct runtimes — Node.js ≥18, Deno, Bun, and browsers — from one codebase and a single dual ESM/CJS build.

The Tamga API protocol specification is the source of truth for wire format, endpoint paths, and enum values. It is not a public document and is not part of this repository — never link to it from any file published to npm or visible to external readers; link to <https://tamga.sh> instead.

**Current state**: the full client surface (license validate/check-in/checkout, license/policy/machine reads, machine/component/process management, offline proof, entitlements, auto-update check, health probe), the offline `.lic`/`.mach` verify/decrypt pipelines, and the typed error model all have real implementations backed by tests (not stubs). **Both** offline file formats are at v2: HKDF-SHA256 key derivation, signed `iat`/`exp`/`jti`/`kid` claims, enforced expiry sharing one clock-skew constant, and outright rejection of v1 files. Machine-file verification is proven against certificates the server itself minted (`test/fixtures/machine-file-v2/`), not fixtures this repo builds. Crypto-touching work has passed a mandatory security review, which found and fixed a real `__proto__`-keyed signature-bypass vulnerability in `src/internal/canonicalJson.ts`.

## GOTCHAS

Server-side realities from the Tamga API protocol specification → Known Server-Side Gaps that constrain what this SDK should (and should not) build:

- **Auth IS enforced server-side, and license-key auth is off by default.** An `Authorization: License <key>` credential is only accepted when the license's policy sets `authentication_strategy` to `LICENSE` or `MIXED`; the column defaults to `TOKEN`, and `NONE` rejects it the same way. Against a default policy every call returns `401 LICENSE_NOT_ALLOWED` — a configuration precondition, not a retryable auth failure, so never put that code in a retry loop. Two more license-key realities: `resetHeartbeat` and `generateOfflineProof` are role-gated and always `403` for it, and an expired license under `expiration_strategy: REVOKE_ACCESS` is rejected at the auth gate with `401 LICENSE_EXPIRED` rather than reaching validate.
- **19 of 24 `ValidationCode` values are reachable today** (gap #4, as amended by M8 and the API patch). `src/models/validation.ts` models all 24 plus a `string & {}` escape hatch — do not write code that treats one of the five unreachable codes (`NOT_FOUND`, `BANNED`, `COMPONENTS_SCOPE_MISMATCH`, `CHECKSUM_SCOPE_MISMATCH`, `VERSION_SCOPE_MISMATCH`) as something a caller needs to handle today; document those as forward-compat only. ⚠️ `ENTITLEMENTS_MISSING` and `FINGERPRINT_SCOPE_MISMATCH` are **no longer** in that set: the server genuinely enforces `scope.entitlements`/`scope.fingerprint` (`validate_license.rs:143-178` `resolve_scope_facts`), so a scoped `validateById` really can return either and every doc surface here must treat them as live outcomes. ⚠️ `TOO_MANY_USERS`, `HEARTBEAT_DEAD` and `HEARTBEAT_NOT_STARTED` are **no longer** in that set since the API patch (every validate endpoint; fingerprint scope under `require_heartbeat`).
- **`429 TOO_MANY_REQUESTS` is live and is handled.** Credential-accepting endpoints run on a tight per-IP budget, and the calls a licensing client makes on a timer sit inside it. `src/transport.ts` parses and caps `Retry-After`, falls back to jittered exponential backoff, and retries `GET` plus seven safe `POST` actions (`validate`, `validate-key`, `check-in`, `check-out`, `ping`, `ping-heartbeat`, `reset-heartbeat`). Creates are excluded on purpose — retrying `POST /machines` can burn a second seat. ⚠️ `ping-heartbeat`/`reset-heartbeat` do **not** end in `/actions/ping` (that is the *process* route) and need their own suffix entries — they were missing, and a dropped heartbeat is what flips a live machine to `DEAD`.
- **`POST /machines` runs the limit checks; they are not all deferred to validate.** The create-time check is routed through the policy's `overage_strategy`, so under `NO_OVERAGE` an over-limit create is refused with `422 MACHINE_LIMIT_EXCEEDED` / `CORE_LIMIT_EXCEEDED` / `MEMORY_LIMIT_EXCEEDED` / `DISK_LIMIT_EXCEEDED`, while an overage-permitting strategy lets the create through and surfaces the same condition later as a `TOO_MANY_*` / `TOO_MUCH_*` `ValidationCode`. `activateMachine` handles both: it normalizes the create-time code onto the validate-time one, and keeps the create→validate→rollback path for the overage case. Do not collapse the two paths — a create-time refusal has no machine to roll back.
- **Machine `memory` and `disk` are MEGABYTES, not bytes.** They feed `licenses.machines_memory_count` / `machines_disk_count` and the activation-time limit check. Reporting 16 GB as `17179869184` inflates the account tally by ~1e6 and gets the next activation refused with `MEMORY_LIMIT_EXCEEDED`. 16 GB is `16384`.
- **`GET /licenses/{id}/entitlements` is not paginable.** The listing is a union of the license's direct attachments and its policy-inherited rows, so no single keyset cursor describes it and the server ignores `page[after]` outright — sending it re-fetches page one forever. `limit` (max 100, default 25) is the only bound, and the response carries no `meta.page`, no `links`, and no total. `listEntitlements` sends 100 when no limit is given and deliberately does not send the cursor; `hasEntitlement`'s `false` is only authoritative below that ceiling. `/machines/{id}/components` is different — its cursor genuinely works.
- **Quick-validate does not always record the validation.** `GET /licenses/{id}/actions/validate` skips the `last_validated_at` write whenever the request carries an `Origin` header, and the response is identical either way. A browser attaches `Origin` to a cross-origin `fetch` itself and script cannot suppress it, so from a browser — this SDK's first-class runtime — quick-validate **never** records a validation. The consequences are real: a license with `machines_count == 0` and a null `last_validated_at` reads as `INACTIVE`, and the check-in-overdue worker keeps firing off the same column. Use `validateById` (the `POST` route, which has no `Origin` branch) when the write matters.
- **RFC 9421 HTTP response signing is fully dead code server-side** (gap #6). No API response is ever signed. This SDK does not implement `Tamga-Accept-Signature` or any response-signature verification — there is nothing to verify.
- **`Tamga-Environment` header is not implemented server-side** (gap #7). Do not add it to `src/transport.ts`, even though it's documented as a planned EE feature — no server code path reads it yet.
- **The machine heartbeat window IS `policy.heartbeat_duration`** (M4 — this reverses the old gap #8 claim, which said the server ignored the field). `Policy::effective_heartbeat_duration_secs` (`tamga-api/src/features/policies/model.rs:262-264`) returns `heartbeat_duration` when set and falls back to 600s only when it is null, and the cull job's claim query agrees (`workers/machine_jobs.rs:213`, `COALESCE(p.heartbeat_duration, 600)`). The **process** window is the one that really is hardcoded — a flat 30s regardless of any policy field — so leave those statements alone. ⚠️ Do not overcorrect into promising adaptivity: `MACHINE_HEARTBEAT_WINDOW_MS` must be documented as the **600s fallback** and `startHeartbeat` as a scheduler the caller sizes by hand — it does not adapt, and every surface stating the policy-driven fact must say so in the same breath or a reader concludes it does. ⚠️ But do **not** write "this SDK cannot read the effective window" either — that was the M4 over-correction, the same shape as the M42 one. There is no `getPolicy`/`getMachine`, yet the value is recoverable: `MachineResource::from` fills `next_heartbeat_at` from `next_heartbeat_at_from_row()` = `last_heartbeat_at + effective_window_secs()` (`features/machines/serializer.rs:42`, `model.rs:111`), and `effective_window_secs()` reads `policy_heartbeat_duration`, which the read queries join in (`queries.rs::find_by_id` selects `p.heartbeat_duration AS policy_heartbeat_duration`). So on a read-backed machine — `verifyAndDecryptMachineFile`, or `generateOfflineProof`'s `machine` — `next_heartbeat_at - last_heartbeat_at` **is** the policy's window. Three caveats every such statement must carry: the ping query has no policy join, so a ping's `next_heartbeat_at` is always `+600s` and is useless for this; the field is `null` until the machine has been pinged once; and it is a snapshot from issue time. Out-of-band is the fallback when no machine file exists, not the only answer. ⚠️ **The "there is no `getPolicy`/`getMachine`" half of this is now stale** — both exist, along with `resolveHeartbeatWindowMs(licenseId)` (which reads `GET /licenses/{id}/policy` and applies the same 600s fallback the server does) and `startHeartbeatFromPolicy`, which sizes its interval off that. Adding them was additive and shipped as a patch; the "non-patch change" note was wrong. What has *not* changed is that plain `startHeartbeat` still does not adapt — it takes the interval it is given. ⚠️ One precision on that last clause: it takes any interval a real caller would give it, but it no longer takes *every* number. **The rule, stated so no reader has to run it: `intervalMs` is clamped to `[1000, 2147483647]` and truncated to an integer; non-finite becomes `1000`. `20000` stays `20000`; `500` becomes `1000`; `1` becomes `1000`; `0`, `-1` and `NaN` become `1000`; `2**31` becomes `2147483647`. Nothing throws.** That is a busy-loop guard, not adaptivity. ⚠️ Do **not** "improve" it into a narrower guard on only the values `setInterval` refuses to honour (non-positive, non-finite, over the ceiling) — that was considered and rejected on measurement. The runtime rewrite is not what does the damage, the rate is, and `setInterval` honours `1` *exactly*: `0` ticks at 1.4 ms and `1` at 1.35 ms, ~740 pings/sec either way (`2` → 2.55 ms, `3` → 3.75 ms, all honoured). A rule that clamps `0` and passes `1` describes where a number came from, not what it does. The floor costs nothing a policy can express, because `heartbeat_duration` is an integer-**seconds** column: the shortest window the server can state is 1s, so a once-a-second ping is inside every policy that exists. ⚠️ **And liveness is judged on *truncated whole seconds*, which is the fact that settles whether the floor is safe on a short window.** `heartbeat_status_within` (`tamga-api/src/features/machines/model.rs:124-129`) computes `let age_secs = (Utc::now() - hb_ts).num_seconds(); let within_window = age_secs <= window_secs;` and chrono's `num_seconds()` returns whole seconds, truncating — verified against chrono 0.4, `Duration::milliseconds(1999).num_seconds() == 1`. So a machine reads `DEAD` only once its age reaches **`window_secs + 1`** seconds, not once it passes `window_secs`. Every window carries one free second. Do **not** restate the rule as "DEAD when age exceeds the window" — that pessimistic reading makes a 1s window look unserveable at a 1s ping (it has 2s of slack) and was the basis of a proposed window-aware floor that was investigated and rejected. What the 1s floor genuinely does cost is `MACHINE_HEARTBEAT_INTERVAL_DIVISOR`'s "two consecutive losses" promise: `heartbeat_duration` 3 is the first window where floor and divisor agree, 2 keeps one spare ping, 1 keeps none, and steady state holds the window in all three. ⚠️ **A non-positive `heartbeat_duration` is unsatisfiable at any rate, and `startHeartbeatFromPolicy` schedules it at the 600s platform-default rate (200s) rather than dividing the raw value.** The deciding fact is the *cull* query, not `heartbeat_status`: `find_and_claim_dead_machines` (`tamga-api/src/workers/machine_jobs.rs:214`) claims rows with `m.last_heartbeat_at < NOW() - make_interval(secs => COALESCE(p.heartbeat_duration, 600))`, and `COALESCE` replaces only `NULL`, so a stored `0` reduces it to `last_heartbeat_at < NOW()` — true for every machine that has ever pinged, at every instant, whatever the interval. ⚠️ The two server paths **disagree** at `0`: the status comparison truncates, so a sub-second ping keeps a `0` window *reporting* `ALIVE` while the SQL comparison still claims the row. Do not cite the status field as evidence a window is holdable — survival follows the cull job. Since no rate rescues the row, the only remaining variable is the cost of failing: 18 requests/hour instead of 3600. ⚠️ This substitutes a **rate, not a window** — `effectiveHeartbeatWindowMs` and `resolveHeartbeatWindowMs` still report `0` verbatim, and must keep doing so; the SDK does not claim a zero window means 600s, only that it cannot schedule against one. Hand-composing the primitives still lands on the 1s floor, because `startHeartbeat` receives a bare number with no provenance and cannot distinguish a misconfigured window from a caller who meant `0`. Seven of the eight SDKs default before dividing; tamga-js was the outlier and has been brought into line. The whole interaction is pinned by a table naming each window value in `test/policy-read.spec.ts`. `heartbeat_duration` has no `CHECK` constraint, so a policy really can store `0` or a negative, and `resolveHeartbeatWindowMs` reports it verbatim by design; hand-composing the two public primitives therefore used to reach `setInterval(0)`. Do **not** describe the accessors as floored — they are not, deliberately, and saying so would be the same over-correction shape as M4/M42. The floor lives in `startHeartbeat` and `startProcessHeartbeat` only.
- **`DEAD` never comes back from a ping, but it does reach this SDK** (M42, as corrected), and it would not mean "culled" anywhere it appears (M5). Two layers, both of which every doc, comment and example here must respect. (1) *A write that **sets** `last_heartbeat_at` cannot report it* — the rule is about that column, not about writes in general, and `PATCH /machines/{id}` is the counterexample: it touches only the descriptive columns, so it still derives a status from the existing `last_heartbeat_at` and **can** answer `DEAD`, judged against the 600s fallback because `queries::update`'s `RETURNING` joins no policy. Never read heartbeat state off `updateMachine`. For the writes that do set the column: `ping-heartbeat` writes `last_heartbeat_at = NOW()` and then computes the status from that same timestamp (`queries.rs:448-470` + `Machine::heartbeat_status_within`), so it returns `ALIVE`/`RESURRECTED` and **never** `DEAD`; `reset-heartbeat` nulls the column (`NOT_STARTED`); `POST /machines` never sets it (`NOT_STARTED`); `validate` never constructs `HEARTBEAT_DEAD`. *Read-backed ones can:* `check_out_machine.rs:54` and `generate_offline_proof.rs:38` both resolve through `queries::find_by_id` — a read that joins `policies` — and serialize with `MachineResource::from`, which calls `heartbeat_status()`. Both are exposed here: `verifyAndDecryptMachineFile` returns a full `Machine` (`src/checkout/machineFile.ts`), and `generateOfflineProof` returns `{ machine, proof }` — `MachineAttributes.heartbeat_status` is modelled on both, so `DEAD` is genuinely observable today. ⚠️ Do not write "`DEAD` is unobservable from this SDK" — that was a wrong over-correction and is exactly the class of claim this pass removes. Scope the statement to the *route*: dead code is a `case DEAD` on a **ping** response, not on a machine file. Never delete the `DEAD` literal from `HeartbeatStatus` or the `heartbeat_status` field. (`GET /machines/{id}` and `GET /machines` are now exposed as `getMachine`/`listMachines`; both resolve through the same policy-joining read, so both can report `DEAD` and `getMachine` is the direct way to observe it.) (2) *Not "culled":* `heartbeat_status*` never consults `require_heartbeat`, while the cull worker returns early whenever it is false (claim query requires `AND p.require_heartbeat`) and that column **defaults to `FALSE`**, so under a default policy nothing is ever culled and a machine stays `DEAD` indefinitely with its row and seat intact; a ping revives it regardless (bare `SET last_heartbeat_at = NOW()`, no resurrection check). ⚠️ **The rule to write down is the positive one:** a heartbeat scheduler must not stop, clear or short-circuit on **any** status (the stop-on-`DEAD` bug shipped in `tamga-python`), and the only terminal signal from a ping is a **`404 NOT_FOUND`**, which is where re-activation belongs. Do not justify that rule with a `DEAD`-from-a-ping scenario — it cannot happen.
- **Machine files are format v2, with the same `alg` grammar and the same signed claims as license files.** `machine_file_alg_str` emits `"{encoding}+{signing suffix}+v2"` — `base64`/`aes-256-gcm` for the encoding, `ed25519`/`ecdsa-p256`/`rsa-sha256`/`rsa-pss-sha256` for the suffix. Both the encoding prefix and two suffixes contain hyphens, so cut at the **first** and **last** `+`; a single `split_once` comparing the whole remainder rejects every file the server emits, and a `contains("+v2")` substring test wrongly accepts `base64+ed25519+v2junk`. A file without `+v2` must be refused: v1 carried no `meta.exp` in the signed payload and zero-padded the license key instead of using HKDF. ⚠️ `alg` is **not** covered by the signature — only `enc`'s string bytes are — so this gate cannot lean on signature validity. An encrypted `enc` is `"{nonce_b64}.{cipher_b64}"`, two separately base64'd halves with the 16-byte GCM tag already inside the ciphertext half (`FieldEncryption::encrypt`, `field_encryption.rs:110`); do **not** decode once and slice 12 bytes off the front. The server's own doc comment at `machine_file.rs:59` says `base64(nonce‖ciphertext‖tag)` and contradicts the code five lines below it — that stale comment is why all eight SDKs implemented the same wrong thing (`tamga-api-internal#2`). Verify the signature first, then split, then decode, then decrypt. The signed payload is `{"data": <Machine>, "meta": <LicenseFileClaims>}` and `meta.exp` is enforced with the license-file path's own `CLOCK_SKEW_TOLERANCE_SECONDS`; `exp` is absent when checkout carried no `ttl`, which is a file that legitimately never expires. ⚠️ **The `kid` claim is no longer inert** — the "nothing selects a key by it, key rotation is a later change" note is stale. `verifyLicenseFileWithKeySet`/`verifyMachineFileWithKeySet` select the signing key by it from a caller-supplied `SigningKeySet` (`src/checkout/keySet.ts`), built either from `GET /signing-keys` (`client.listSigningKeys`/`getSigningKeySet`) or from keys pinned in the binary. Shipped additively as a **patch**: the single-key entry points are untouched, and on a `0.x` package a minor is the breaking channel that `^0.4` consumers never receive. Four rules that must not be "simplified" away. (1) **`kid = lowercase_hex(SHA-256(<public key BASE64 STRING>)[0..8])`** — the server hands `key_id()` the stored base64 `&str`, never the 32 decoded bytes, and decoding first yields a plausible id matching nothing it emits. Pinned by independent vectors *and* a negative vector in `test/fixtures/signing-keys/`, and cross-checked against the kids the server stamped into all 12 certificates in `test/fixtures/machine-file-v2/manifest.json`. (2) **Retired keys stay in the set** — filtering to `status === "active"` reinstates the exact lockout this fixed. (3) **Every held key is tried against the signature before `enc` is decoded**; the `kid` only labels a failure (held = forgery, unknown = stale set). `CheckoutError.reason` says which check failed. (4) **A fetched set is indexed by the resource `id`, which *is* the kid**; the local computation only cross-checks, and a disagreement is reported on `SigningKeySet.mismatches` rather than thrown. An unknown kid raises the new `SigningKeyError` (`"unknown-key-id"`, or `"no-published-signing-key"` when the file names `SHA-256("")` = `e3b0c44298fc1c14`, the id every file gets from an account whose `ed25519_public_key` column was never populated); a *known* kid whose signature then fails still raises `CheckoutError`/`"crypto"`. Keeping those two apart is the whole point. ⚠️ `verifyMachineFileWithKeySet` is Ed25519-only and refuses other suffixes on the `alg` gate, because `GET /signing-keys` publishes Ed25519 keys and nothing else. Do **not** justify that with tamga-rust's claim that both checkout handlers hash `account.ed25519_public_key` whatever scheme signed — this repo's 12 server-minted fixtures contradict it, carrying four distinct kids, one per scheme, each hashing that scheme's own key (`test/signing-key-id.spec.ts` pins the measurement).
- **Freshly-created policies default to enum strings that don't exist** (gap #9) — `overage_strategy: "DENY_ACCESS"` and `heartbeat_resurrection_strategy: "NO_RESURRECTION"` are not real variants and silently behave as `NO_OVERAGE`/`NO_REVIVE`. `src/models/policy.ts` types these fields as the real enum unioned with `string & {}` for exactly this reason — don't "fix" the type to reject them.
- **The release/auto-update endpoint works, and `204` means two things.** An earlier directive here — that `GET /releases/actions/upgrade` crashes at runtime and that no artifact-download route exists — was wrong on both counts. `checkForUpgrade` now ships. Two claims that replaced it were also over-broad and are corrected here: it is **not** unconditionally public, and `204` does **not** mean "already current".
  - Access runs through `enforce_distribution_strategy` on the *product*: `Open` answers unauthenticated, `Licensed` needs a credential carrying `release.read`, `Closed` needs an admin/developer/product token. "Public" is a property of the product, not of the route.
  - `204 No Content` is returned both when no newer release exists (`upgrade_release.rs:62-63`) **and** when one exists that this license is not entitled to (`:92-100`). The server's own comment gives the reason: a distinct refusal would leak "there is a newer version and you cannot have it". So never report `undefined` as "you are up to date" — the phrasing is *no update is available to you*. A **suspended** license is a third outcome and is not collapsed: it answers `403`.
  - `channel` is required at this SDK's surface (omitting it drops the channel predicate and matches *every* channel, alpha and dev included), `constraint` defaults to patch-only `~x.y.z` when omitted (so an updater that omits it never sees a minor bump), `product` is the product **UUID** and not its code, `version` must parse as semver (`422 INVALID_VERSION`), and the handler uses a bare Axum query extractor so a malformed query comes back as plain-text `400`, not JSON:API — `sendJsonApiOptional` decodes that error path defensively for exactly this reason.
  - ⚠️ **The "artifact download is walled off by a permission the license-key role does not hold" half of this is now stale** (M25). `tamga-api@e6d317b` added **`artifact.download`** to `Role::LicenseToken` (`shared/authz/mod.rs:265`) and routed a real handler. ⚠️ Be precise about which half moved: `artifact.read` (`:263` before the commit, `:264` after) was **already** in that role's default set, so listing and showing an artifact were never the blocked part — only fetching its bytes was, and that is why the read routes went unmodelled too (metadata you cannot act on is not worth a surface). The commit adds exactly one line, twice: once to `Developer` and once to `LicenseToken`. Three routes are now reachable and modelled here: `listReleaseArtifacts` (`GET /releases/{id}/artifacts`, keyset), `getArtifact` (`GET /artifacts/{id}`) and `getArtifactDownloadUrl` (`GET /artifacts/{id}/actions/download`). What has **not** changed is that `artifact.create/update/delete` are absent from that role, so create/update/delete/upload stay unmodelled — nothing this SDK could send would be authorized. Do not add them. Three traps, all measured, none of which may be "simplified" away. (1) **The download action answers `303 See Other`** at a presigned storage URL and `doFetch` passes no `redirect` option, so `fetch`'s default `"follow"` applies. The Fetch standard deletes `Authorization`/`Cookie` only across an **origin** boundary — measured on Node 22, Deno 2.9 and Bun 1.3: a cross-origin hop arrives with no credential, a **same-origin** hop arrives carrying `Authorization: License <key>` intact, and `s3_endpoint` + `s3_force_path_style` exist precisely to allow same-origin path-style storage. So the leak is real but scoped to same-origin storage; do **not** restate it as "fetch always hands the key to the storage host", and do **not** conclude from the cross-origin stripping that following is safe — the follow also lands on the artifact *bytes*, which `sendJsonApi` buffers into a string inside the per-attempt deadline before failing to parse them (an artifact may be 1 GiB). The SDK sends `?redirect=false` **and** pins `redirect: "manual"`; `RequestOptions.redirect` and `assertNotRedirect` in `src/transport.ts` are that net, and the browser arm checks `response.type === "opaqueredirect"` because a browser reports status `0`, not `303`. (2) **`ArtifactAttributes` is `rename_all = "camelCase"` AND carries explicit `#[serde(rename = "created")]`/`#[serde(rename = "updated")]`** (`artifacts/serializer.rs:20,34-37`), so the wire names are `redirectUrl` but bare `created`/`updated` — applying camelCase uniformly yields two permanently `undefined` timestamps. Same split as `releases`. (3) **A `403` from the download action is not necessarily an auth misconfiguration**: the handler runs `releases::service::enforce_release_access` on the owning release — distribution strategy, suspension, expiry, entitlement — after the permission check (`download_artifact.rs:46-59`), so a `CLOSED` release's binary is refused to a caller that genuinely holds `artifact.download`. One more code-level trap: a bad `ttl` is **`PRESIGN_TTL_INVALID`** (`artifacts/service.rs:33`), not the `TTL_INVALID` the checkout routes send (`check_out_license.rs:48`), so it arrives as the generic `ApiError` and **not** as `TtlInvalidError`. Do not "unify" them.
- **`GET /machines` is offset-paginated; every other list in this SDK is keyset.** The nested sub-resource lists (`/machines/{id}/components`, `/machines/{id}/processes`, `/licenses/{id}/entitlements`) are hand-written keyset queries — `limit` + `page[after]`, no totals. The top-level collection goes through the server's shared `list_query` module, which is plain `LIMIT`/`OFFSET`: `page[number]` + `page[size]`, and a real `meta.page` of `{number, size, total, totalPages}`. Do not model a cursor for it, and do not send `page[number]` at a keyset route — both are ignored silently, in opposite directions. There is also **no `filter[fingerprint]`**: the only fingerprint lookup is the free-text `filter[q]`, an `ILIKE '%term%'` across `name`/`hostname`/`fingerprint`, so `findMachineByFingerprint` re-checks the field exactly after searching. And the `machines` resource does **not** serialize `license_id`, so a machine's owning license is only knowable from having filtered on it.
- **A license key is not confined to its own license on the read routes.** `require_license_scope` — the guard that stops a license-key credential naming a different license — is called by `validate`, `validate-key` and `check-out`, but **not** by `get_license` or `get_license_policy`. The `LicenseToken` role holds `license.read` by default, so a key can read any license in the account and `attributes.key` comes back in plaintext. Reported upstream; there is no client-side fix, and no doc surface here may describe these reads as license-confined.
- **`getPolicy` is unreachable with a license key, `getLicensePolicy` is not.** `GET /policies/{id}` requires `policy.read`, which is absent from `Role::LicenseToken`'s default permission set, so it answers `403` regardless of `authentication_strategy`. `GET /licenses/{id}/policy` requires only `license.read`. Any policy read written for an embedded client must go through the license.
- **Nothing server-side reaps a stale process row.** `machine_jobs::find_and_claim_dead_processes` and `process_process_heartbeat` exist and are tested, but the scheduler's `dispatch` has no arm that calls them — only `cull_dead_machines` is wired. `licenses.machines_processes_count` is decremented solely by an explicit `DELETE /processes/{id}`, so a client that registers a process per launch and never deletes one eventually gets `422 TOO_MANY_PROCESSES` on every start. `deleteProcess` and `listMachineProcesses` exist for this; `dispose()` stops timers but deliberately deletes nothing.
- **`policy.check_in_interval`'s wire values are `daily`/`weekly`/`monthly`/`yearly`, and `CheckInInterval` now says the same** (M9, corrected in 0.4.0 — it previously said `day`/`week`/`month`/`year`, spellings the column rejects, so the union could not describe any policy that exists). The DB `CHECK` constraint and `enums::CHECK_IN_INTERVALS` both allow only the `-ly` forms; that constraint is what makes the closed union safe here, and it is why this field needs no lenient `resolve*` companion the way `overage_strategy` and `heartbeat_resurrection_strategy` do — there is no bogus default to absorb. Do not add one: mapping `"day"` → `"daily"` would re-legitimise a spelling the database has never accepted. What must keep holding is that an *unrecognised* value still **degrades** rather than rejects — TypeScript validates nothing at runtime and this SDK adds no runtime guard, so a future vocabulary change decodes intact; `test/policy-read.spec.ts` pins both halves. ⚠️ Related upstream defect, not an SDK concern and not fixed by M9: `validate_license.rs::check_in_interval_days` matches on the `day`/`week`/`month`/`year` spellings the database cannot hold, so every configured interval falls through its `_ => 30` arm — a `"daily"` policy is enforced at 30 days and `check_in_interval_count` is discarded rather than multiplied (`tamga-api-internal#3`). No doc surface here may describe this field as driving a deadline.
- **`policy.max_memory` and `policy.max_disk` are not modeled, and that is the finished state** (M38, done in 0.4.0). Both exist on the server's `Policy` model (`policies/model.rs:187-188`) and both are genuinely enforced during validation (`:302`, `:309`) and at machine create, but `policies/serializer.rs` emits `max_machines`/`max_cores`/`max_uses`/`max_processes`/`max_users` and skips them — so no route this SDK calls can populate either. They were previously declared on `PolicyAttributes` as optional properties documented as "always `undefined`", which only invited callers to branch on a value that never arrives. `test/policy-model.spec.ts` now pins `keyof PolicyAttributes` against a transcription of the serializer's field list as a **type-level** equality, so re-adding either — or dropping a field the serializer does emit — fails `pnpm typecheck` rather than passing quietly. Do not re-add them; the two limits are observable only as `TOO_MUCH_MEMORY`/`TOO_MUCH_DISK` on a failed validation or `MEMORY_LIMIT_EXCEEDED`/`DISK_LIMIT_EXCEEDED` on a refused create.

- **Fingerprint canonicalisation is a pure function and reads NO hardware identifiers** (M-fingerprint). `src/fingerprint.ts` turns caller-chosen `{label, value}` components into `lowercase_hex(SHA-256(UTF-8("tamga-fingerprint-v1" + US + join(US, sort_bytewise(components)))))`, where `US` is U+001F. The measured defect it fixes: the server stores `fingerprint TEXT NOT NULL` with no length limit, no `CHECK` and no normalisation, unique per `(license_id, fingerprint)`, and every SDK sent the caller's string byte-for-byte — so `"ABC-123"`, `"abc-123"` and `" ABC-123 "` were three seats. ⚠️ **Do not add hardware-identifier reading.** What identifies a machine is a product decision (a cloned VM template shares them, a container has none, a replaced motherboard changes them, a browser has nothing to read), and no default is right for both a desktop app and a Kubernetes sidecar. ⚠️ **Do not add NFC normalisation**, even though `String.prototype.normalize` is built in and it would cost nothing here — that is precisely the trap. NFC needs a new dependency in Rust and Go and ICU or hand-rolled tables in C11, and a rule eight ports cannot implement identically yields two fingerprints for one machine depending on which SDK the app used. Same for case folding: lowercasing a base64 or hex identifier corrupts it, and `case_preserved` pins it. ⚠️ **The trim is ASCII-only and must stay that way** — `String.prototype.trim` strips the whole Unicode `White_Space` set (U+00A0, U+2028, ...), which the other seven ports do not, so using it reintroduces the same cross-port divergence in a less visible place. Rejections **throw** and never repair: stripping a control character or de-duplicating a label would map two different inputs onto one seat. ⚠️ **One premise about this rule is wrong and must not be re-asserted: the bytewise-UTF-8 sort is *not* observably different from `Array.prototype.sort`'s UTF-16 order here, and no test can pin a divergence.** Labels are ASCII printable, cannot contain `=`, and duplicates are rejected, so two distinct components always differ at a label byte or at the `=` terminating whichever label prefixes the other — both below `0x80`, where the two orderings coincide. Measured exhaustively over 8 732 016 valid pairs: zero divergent orderings, and mutating `parts.sort(compareUtf8)` to `parts.sort()` leaves the whole suite green. `compareUtf8` stays anyway because it is what the shared cross-port spec states and because `parts.sort()` would only be equivalent *because* of an invariant established in `validateLabel` a hundred lines away — a v2 that relaxes labels would silently break it. `test/fingerprint.spec.ts` proves the equivalence is structural and holds the control showing the comparators do differ on bare values; do not "strengthen" it into asserting a divergence that cannot occur. ⚠️ Related: **"bytewise over UTF-8" and "code-point order" are the same ordering** — UTF-8 is built so byte comparison equals code-point comparison — so there is no test distinguishing *those* two either, and a port that writes one is testing nothing (tamga-go wrote one, watched the mutation survive, and deleted it). **The two sort mutations that do bite, in every language, are: sort key = whole `label=value` component vs. label only** (`a-b=y` precedes `a=x` because `-` is 0x2d < `=` 0x3d, and label-only sorting reverses it) **and case-sensitive vs. case-insensitive** (`B=2` precedes `a=1`, 0x42 < 0x61, and folding reverses it). Both are pinned and both were confirmed to survive before those tests existed. ⚠️ **Read the vector file as UTF-8 explicitly.** tamga-python shipped green locally and failed on `windows-latest` only, because `Path.read_text()` used the cp1252 platform codec and the `é` in `non_ascii_value` decoded as mojibake — one SDK disagreeing with itself across two operating systems, which is the exact failure the shared spec exists to prevent arriving by a route the spec does not cover. Every other vector is pure ASCII and would look green through a mis-decoding reader, so `non_ascii_value` is the only load-bearing one. Both `test/fingerprint.spec.ts` and `scripts/smoke.mjs` assert the decoded code points *before* any digest, so a mis-decode names its own cause instead of surfacing as a hash mismatch; the smoke copy matters because Deno and Bun are where a decoding difference would actually show up. Vectors live in `test/fixtures/fingerprint/fingerprint.json` (shared across all eight SDKs, generated by an independent SHA-256 implementation — see its `PROVENANCE.md`); both arrays are iterated and their lengths asserted, so adding a vector needs no test edit and removing one fails loudly.

## Critical Dependency Notes

**Ed25519 and ECDSA P-256 use `@noble/curves`; HKDF-SHA256 uses `@noble/hashes`, not `crypto.subtle`.** These are audited, pure-TypeScript, zero-native-dependency libraries with identical behavior across all 4 target runtimes. `crypto.subtle`'s Ed25519 support in particular is inconsistent across Node/Deno/Bun/browser today — the asymmetric-signature surface for Ed25519/ECDSA is deliberately kept off WebCrypto entirely rather than branching per runtime. Do not "simplify" ed25519.ts/ecdsa.ts onto WebCrypto.

**The account's RSA public key is PKCS#1, not SPKI, whatever the server's comments say.** `aws-lc-rs`'s `RsaKeyPair::public_key()` returns a bare `RSAPublicKey` DER (`SEQUENCE { modulus, exponent }`, 270 bytes for RSA-2048), and that blob is what lands in `accounts.rsa_public_key` and in every published key. The server calls it SPKI in `key_material.rs:37` and `license_signing.rs:142`, and its `rsa_public_key_is_spki_der` test only asserts `len > 256` — which PKCS#1 also satisfies — so nothing there catches it. WebCrypto has no PKCS#1 import format, so `src/crypto/rsa.ts::toRsaSpki` detects the encoding (first inner tag: `0x02` INTEGER = PKCS#1, `0x30` SEQUENCE = SPKI) and wraps when needed. Do not "simplify" that away, and do not document either RSA entry point as SPKI-only — `verifyRsaPkcs1`, `verifyRsaPss`, `verifyOfflineProof` and the RSA branches of machine-file verification all depend on it.

**`@noble/curves` takes a message DIGEST, not a message.** `p256.verify(sig, msgHash, pk)` runs `bits2int` over whatever it is handed and silently truncates, so passing raw bytes does not throw — it just verifies against the wrong thing. The server signs `SHA-256(enc)` (`ECDSA_P256_SHA256_ASN1`), so `src/crypto/ecdsa.ts` hashes explicitly before calling `verify`. It did not, and because the test fixture builder made the identical mistake on the signing side, the round trip was green while no server-issued ECDSA machine file could be verified. Hash explicitly rather than via noble's `prehash` option — that option is not present across the whole `^1.6.0` range this package allows.

**Never test offline verification against a fixture this repo generated.** `test/helpers/checkoutFixtures.ts` builds `.lic`/`.mach` files, and it can only encode this repo's *belief* about the wire format; when the belief was wrong it reproduced the error on the signing side and CI stayed green over a verifier that could not open anything the server emitted. Machine-file interop is tested against `test/fixtures/machine-file-v2/` — server-minted certificates, iterated from `manifest.json` by `test/machine-file-server-fixtures.spec.ts`, so a new fixture dropped into that directory is exercised with no test edit. `scripts/smoke.mjs` re-runs the same set against the built `dist/` on Node, Deno and Bun. Use `checkoutFixtures.ts` only for the negative/structural space the server will not mint (a refused scheme, a caller/file mismatch, a wrong key).

**RSA (PKCS#1 v1.5 + PSS) verify uses native `crypto.subtle` (WebCrypto), NOT `@noble/curves`.** `@noble/curves` is a pure elliptic-curve library (Ed25519, secp256k1, P-256, BLS12-381) with **no RSA support at all**, and WebCrypto's RSA verify operations are stable across all 4 target runtimes (unlike its Ed25519 support). `src/crypto/rsa.ts`'s module doc comment documents this in full. Because WebCrypto is Promise-based, `verifyRsaPkcs1`/`verifyRsaPss` — and consequently `src/proof.ts` and the RSA branches of `src/checkout/machineFile.ts` — are `async`, unlike the synchronous `@noble/curves`-backed `verifyEd25519`/`verifyEcdsaP256`.

**AES-256-GCM uses native `crypto.subtle` (WebCrypto) directly, with zero npm dependency.** AES-GCM is a symmetric primitive with universal, stable, hardware-accelerated WebCrypto support across all 4 runtimes — there's no correctness or portability reason to pull in `@noble/ciphers` or hand-roll it. Do not move this onto `@noble/*` for "consistency" with the asymmetric primitives above; the two choices (and now RSA's WebCrypto choice too) are pinned to per-primitive runtime-compatibility realities, not a general library preference.

**Both file formats derive their AES key with HKDF-SHA256 (`src/crypto/hkdf.ts`), with different parameters.** License files: `salt = "tamga:license-file-key-v1"`, `ikm = <license key>`, `info = "license-file"`. Machine files: `salt = "tamga:machine-file-key-v1"`, `ikm = <license key>`, `info = <fingerprint>`. The pre-v2 zero-pad/truncate transform and its `naiveKey.ts` module were **deleted, not deprecated** — keeping them exported would let a caller silently opt back into the weaker derivation. Don't collapse the two derivations into one helper: the differing salt/`info` is what keeps a machine file undecryptable anywhere but on the machine it was issued for.

**Package manager is pnpm via Corepack** (`packageManager` field in `package.json`). Do not add `package-lock.json` or `yarn.lock`; do not run plain `npm install`.
